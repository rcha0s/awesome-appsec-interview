# A new doc shape for architecture-review-level decisions

ADR-0001 and ADR-0002 lock a shape that assumes one system under discussion: mental model, How it works, Quick reference (one invariants table), Attack techniques (a flat numbered list), Defense (Real fix / Defense in depth), Detection, Interviewer probes, Sources. Every doc added so far fits that shape, including the hub docs (30, 31, 32), because a hub still indexes attack-shaped deep dives and is itself attack-shaped.

A security architecture review does not ask "how does this one system fail." It asks "how should this system do authentication, and what have we not thought about yet." That's a decision across several realistic options, each of which forks by deployment context (a web session and a service-to-service credential are not the same design problem), and each of which drags along secondary features with their own security considerations (password auth is never just "hash the password": password reset, forgot-password, remember-me, and account recovery are separate design decisions with separate failure modes). None of the existing shape's sections fit this. Forcing it through `## Attack techniques` would flatten unrelated attack surfaces from several different mechanisms into one list, which is the opposite of a comparison. Forcing it through a single invariants table loses the per-context, per-option structure entirely.

We are locking a second, parallel doc shape for this kind of doc, called an **architectural control doc** (see the `CONTEXT.md` glossary entry). It keeps the parts of the existing convention that are not shape-specific: the blockquote mental model, the Interview frequency tag, `<sup>[[N]](#refN)</sup>` citations resolving to an anchored numbered Sources list, and the writing-style rules. It replaces the system-specific sections with:

1. `## Where this decision forks`: states the axis this topic's security profile actually diverges across. Deployment surface (web / mobile / desktop-native / service-to-service) fits authentication and session management. Other topics fork on a different axis (secrets management by environment/lifecycle stage, authorization by actor type) and the doc says so explicitly rather than forcing every topic through the same four buckets.

   Before any of that, the mental-model blockquote grounds the topic in its established first-principles framework, named, not paraphrased. Authentication is the three factors (something you know, something you have, something you are, per NIST SP 800-63B); authorization has RBAC/ABAC/ReBAC as its access-control models; encryption and key management has the CIA triad and Kerckhoffs's principle. These docs sit at the top of the site's information hierarchy, so a reader without the framework already in mind has nothing to hang the rest of the doc on. This is a real requirement, not a nice-to-have: the first draft of the Authentication pilot skipped it and jumped straight to "how do platforms implement auth," and the framework had to be added back in review.
2. One `### <context>` subsection per fork, each with an options table (`Option | Best for | Avoid when | Status (2026) | Deep dive`) and a design-considerations table for that context's sub-feature gaps (`Consideration | Why it matters | Design guidance | Deep dive`). The design-guidance cell is one line: name the gap, why it matters, the shape of the right choice. It is not a defense-in-depth writeup and it does not explain the attack the gap is vulnerable to; that depth stays in the linked deep-dive doc.

   The design-considerations table caps at 5-8 rows: the gaps a Staff-level interviewer would actually probe on, or that materially change the design. The first pilot doc (Authentication) shipped with 15-26 rows per context and the first round of feedback on it was that a table that long is unreadable, exactly the failure mode a fast-skim design checklist exists to avoid. Every other sub-feature gap worth a mention still gets one, but as a single compact closing line under the table: comma-separated, gap name plus a three-to-six word reason, linking to whichever deep-dive doc(s) cover the rest. The deep-dive docs are already "the other doc that goes into details" for every one of these; the closing line just points at them instead of re-deriving a full row.
3. `## Recommended defaults by context` and `## Migration path`, the fast-skim answer and the practical rollout guidance a Staff-level review actually needs.
4. `## Interviewer probes`, reframed for tradeoffs ("when would you choose X over Y") and gaps ("what's commonly missed when...") instead of mechanism explanations.

`## How it works`, `## Attack techniques`, and `## Defense` (Real fix / Defense in depth) do not appear in this shape. Mechanism depth and full defense treatment live in the existing per-vulnerability docs; an architectural control doc's whole purpose is comparing and linking to them, not repeating them.

This shape is documented in `.claude/skills/add-architectural-control/SKILL.md`, which produces docs in this shape the way `add-appsec-topic` produces docs in the ADR-0001/0002 shape. The two skills are siblings, not a replacement; `add-appsec-topic` continues to own every per-vulnerability and per-protocol deep dive.
